# 稽古 · 更新服务托管说明（给开发者）

稽古有两条独立的更新通道，两条都**不需要任何服务器程序、数据库或后端代码** ——
要么直接从 GitHub Releases 抓，要么把几个静态文件放到任何能直链访问的地方。

用户侧的统一行为是：**启动后台静默检查 → 悄悄下载好 → 才弹一次
「新版本已下载完成，现在重启更新吗？」**。用户不点，包就留在本地下次启动再问，
不需要盯下载进度条。

---

## 一、更新源怎么配

更新源就是**一行文本**，按优先级从三处取：

1. 环境变量 `JIGU_UPDATE_BASE`（调试用，也供 `--test-update` 接管）
2. exe 同目录的 `update_base.txt`（分发时改这个，用户升级程序也不会被覆盖）
3. 编译内默认值 `github:rdfghjgyuytytrudthgc/jigu-app`

这一行有两种写法：

| `update_base.txt` 内容 | 模式 | 说明 |
| --- | --- | --- |
| `github:owner/repo`（`owner/repo` 亦可） | **GitHub Releases**（默认） | 读该仓库「最新 Release」的附件。发版即生效，不用手工上传任何清单 |
| `https://…` / `http://…` / `file://…` | 静态基址 | 自建镜像、内网共享目录、离线测试都用这种 |

```
# 默认：跟着发布仓库走，零配置
github:rdfghjgyuytytrudthgc/jigu-app
```

> 代码内**没有任何绝对路径**，一切以 `AppDomain.CurrentDomain.BaseDirectory` 为基准，
> 所以程序装在 `C:\Program Files\稽古`、`D:\软件\稽古` 还是 U 盘上都能正常找到自己的文件。

### 史料想单独走一个源

史料（语料与标签表）的迭代频率远高于程序本体。在 exe 同目录再放一个
`data_base.txt`，即可让数据通道独立于程序本体：

```
https://your-mirror.example.com/jigu-data
```

解析顺序：`JIGU_UPDATE_BASE` → `JIGU_DATA_BASE` → `data_base.txt` → 跟随程序本体源。
**不配也能用** —— 默认情况下数据文件和安装包挂在同一个 Release 上。

### GitHub 模式实际发的是什么请求

```
GET https://api.github.com/repos/<owner>/<repo>/releases/latest
Accept: application/vnd.github+json
```

* 基址可用 `JIGU_GITHUB_API` 覆盖 —— 这也是**离线测试 GitHub 模式**的入口（见第四节）。
* 同一轮检查里，史料与程序两次检查**共用一次 API 请求**（结果缓存 5 分钟），
  不会把限流配额浪费掉两次。
* 未认证调用 `api.github.com` 有 **60 次/小时/IP** 的限制。单机一次检查一个请求、
  又做了缓存与 6 小时周期复查，正常够用；同一出口 IP 后面有大量用户时可能撞到 403，
  届时**静默降级**（当作没有更新，不弹框）。真遇到就改用静态基址模式。

## 二、程序本体更新（app_version.json）

GitHub 模式下**什么都不用手工做**：`.github/workflows/release.yml` 会在打 tag 时
自动生成 `app_version.json` 并挂到 Release 上（见第五节）。

静态基址模式下，这个文件要你自己放到托管根目录：

```json
{
  "version": "1.7.0",
  "url": "jigu-installer-v1.7.0.exe",
  "sha256": "安装包文件的 SHA-256（小写十六进制）",
  "notes": "本次新增：\n· 全量史料外置与倒排索引\n· 修复长时间运行的内存问题",
  "mandatory": false
}
```

| 字段 | 说明 |
| --- | --- |
| `version` | 版本号，按 `主.次.修订` 比较。**必须大于用户本地版本**才会提示；比本地旧的一律忽略（不会把用户降级） |
| `url` | 新安装包的地址。写相对文件名最稳（程序按当前源解析）；也接受绝对 `https://`/`http://`/`file://` |
| `sha256` | **强烈建议填写**。程序先校验再替换，防篡改与防下载不完整；留空则跳过校验 |
| `notes` | 更新说明，显示在弹窗里（用 `\n` 换行）。程序侧最多显示 600 字，超了截断 |
| `mandatory` | 设为 `true` 时确认框只剩「好」一个按钮，不提供「稍后」 |

**取 SHA-256（Windows 自带，无需装工具）**：

```powershell
Get-FileHash .\稽古-安装包.exe -Algorithm SHA256
```

### 没有 app_version.json 时会怎样

GitHub 模式下如果某个 Release 忘了挂这个文件，程序会**从 Release 自身推导**：
版本号取 tag（`v1.7.0` → `1.7.0`），下载地址取名为 `jigu-installer-*.exe` 的附件，
哈希从 `SHA256SUMS.txt` 附件里按文件名查。所以「只打一个 tag 就发版」也是通的 ——
这正是 CI 的兜底路径。

### 用户侧完整流程

1. 程序启动，后台线程静默检查（不打扰用户）
2. 发现新版本 → 后台下载到 `pending\稽古-update.exe`，同时写一份
   `pending\pending.json` 记录版本 / 哈希 / 说明
3. 下载**完成后**才弹窗：「新版本 v1.7.0 已下载完成（14.5 MB）（当前 v1.6.1）。
   本次更新内容：…　点「是」立即重启更新；点「否」这次先不更新，下次启动时再问你。」
4. 点「是」→ 拉起替换助手 → 等旧进程退出 → 用 `--extract-to` 覆盖安装目录 → 自动重启
5. 点「否」→ 包留着。**下次启动时**会重新发现它并再问一次

下载失败或中途退出留下的**半截包会被自动清掉**（`pending.json` 里记着磁盘上那个包的
真实哈希，下次启动比对不上就删）；版本不比当前新的残留同样会被清掉。

## 三、史料数据更新（data_version.json）

`data_version.json` 由 `build.ps1` 自动生成，产物在 `dist\update\` 里：

```json
{
  "version": "0.1.0",
  "generated_at": "2026-09-24T00:00:00Z",
  "source_url": "https://github.com/rdfghjgyuytytrudthgc/jigu-app",
  "books": { "corpus": "<corpus.json 的 SHA-256>" },
  "files": {
    "labels.json":    "<labels.json 的 SHA-256>",
    "stopwords.json": "<stopwords.json 的 SHA-256>"
  },
  "paths": {
    "corpus": "corpus.json",
    "labels.json": "labels.json",
    "stopwords.json": "stopwords.json"
  }
}
```

* `books` 里每一项是「史料名 → 该文件 SHA-256」，下载后按该名并进本地语料。
  **`corpus` 是保留键**：它指代整份 `corpus.json`（程序也是拿它跟磁盘上整个文件的哈希
  比对），所以它带来的内容是**整份替换**本地语料，而不是当成「多出来的一本书」追加 ——
  当成追加的话本地原有史料不会消失，语料会翻一倍；
* `books` 里除 `corpus` 之外的键才是「某一部书」，合并时按**文档自己的 `book` 字段**
  替换同名分组（该字段缺失才退回用文件名），所以新增的补遗书就是新加一组，
  且文件名与书不必同名。同一次清单里两者可以并存：先整份替换，再把按书的那些叠上去；
* **只用 `corpus` 一条是最省事的写法，也是 build.ps1 默认产出的形态**：这样合并结果与
  发布的那份逐字节相同，哈希对得上，`Check` 判为"已是最新"，不会重复下载。
  一旦同一次清单里带了按书下发的条目，本地 `corpus.json` 就成了「远端整份 + 补遗」的
  超集，它跟发布侧那份 `corpus.json` 的哈希**必然**不相等 —— 于是每轮检查都会把整份语料
  重下一次、重写一遍、重建一次索引（内容不会错、也不会重复，只是白跑）。
  所以按书拆分适合"补遗量小且更新不频繁"的场景；要避免这点开销就只发整份；
* `files` 里每一项是**整体替换的平文件**（不合并，下载后原样覆盖），目前是情境标签表
  `labels.json` 与查询停用词表 `stopwords.json`。这两张表是检索质量的主要可迭代资产，
  改它们不必重新编译 exe，所以单独放在这里；
* `paths` 是「史料名／文件名 → 相对路径」，程序按这个路径下载；
* 想按史书分文件下发就写多条，例如：

```json
{
  "version": "2.1.0",
  "books": {
    "corpus":    "<corpus.json 的哈希>",
    "史记补遗":   "<shiji-extra.json 的哈希>"
  },
  "paths": {
    "corpus":    "corpus.json",
    "史记补遗":   "books/shiji-extra.json"
  }
}
```

新增的史料文件格式（与现有语料一致）：

```json
{
  "book": "史记补遗",
  "items": [
    {
      "chapter": "项羽本纪",
      "title": "陈平反间，范增去楚",
      "original": "……原文……",
      "translation": "……白话译文……",
      "figures": ["项羽", "范增"],
      "decision": "……关键决策……",
      "outcome": "……最终结果……",
      "themes": ["将帅不和", "内部分裂"]
    }
  ]
}
```

**用户侧会发生什么**：程序启动 → 静默比对哈希 → 只下载变化的文件 → 校验
SHA-256 与 JSON 合法性 → 按 `book` 合并进本地 `corpus.json` → 重建倒排索引 →
界面上自动刷新。**失败一律静默降级**，继续用本地旧数据，绝不弹错误框。

> 注意 `labels.json` / `stopwords.json` **不随 `dist\稽古\` 出厂**，外置文件优先，
> 内嵌副本只作兜底。所以刚装好的程序会去源上取一次这两张表，之后哈希一致就不再动。

## 四、手动触发与自测

程序内置了几个命令行参数，方便发版前自测：

| 命令 | 作用 |
| --- | --- |
| `稽古.exe --selfcheck 报告.txt` | 校验界面资源 / 语料加载 / C# 检索 Top3 / 更新清单 |
| `稽古.exe --test-update <源>` | 走完「检查→下载→校验→解压替换」全流程并输出报告（不弹窗） |
| `稽古-安装包.exe /silent /dir=<目录>` | 静默安装到指定目录（批量部署用） |
| `稽古-安装包.exe --extract-to <目录>` | 把安装包内容解开到指定目录（热替换内部使用） |
| `稽古-卸载.exe /uninstall /silent` | 静默卸载 |

`--test-update` 的源参数**两种模式都收**，所以它是验证整条链路的主力：

### 静态源（自建镜像、离线目录都走这条）

`build.ps1` 会把整套更新通道产物放进 `dist\update\`，直接拿它当"远端"即可
（想验证"真的有新版本"就把里面的 `app_version.json` 版本号改大）：

```powershell
.\稽古.exe --test-update file:///D:/DSH/jigu-app_new/jigu-app/dist/update
```

报告里应出现 `RESULT: UPDATE SIMULATION OK (0 fails)`。

### GitHub 模式（不需要联网）

因为 `JIGU_GITHUB_API` 可以指向任何地方，而程序读 `file://` 是支持的，
所以伪造一份本地 Release 就能把 GitHub 模式走通 —— 不需要真的联网，也不需要
改 hosts。目录结构照着 API 的路径摆：

```
test-gh/
└─ repos/rdfghjgyuytytrudthgc/jigu-app/releases/latest      ← 一份 Release JSON
```

`latest` 文件的内容（附件的 `browser_download_url` 指到本地文件即可）：

```json
{
  "tag_name": "v9.9.9",
  "body": "本次更新说明的第一行",
  "assets": [
    { "name": "jigu-installer-v9.9.9.exe", "browser_download_url": "file:///D:/.../稽古-安装包.exe", "size": 15249920 },
    { "name": "SHA256SUMS.txt",            "browser_download_url": "file:///D:/.../SHA256SUMS.txt",   "size": 92 },
    { "name": "data_version.json",         "browser_download_url": "file:///D:/.../data_version.json","size": 716 },
    { "name": "corpus.json",               "browser_download_url": "file:///D:/.../corpus.json",      "size": 270911 },
    { "name": "labels.json",               "browser_download_url": "file:///D:/.../labels.json",      "size": 21200 },
    { "name": "stopwords.json",            "browser_download_url": "file:///D:/.../stopwords.json",   "size": 2318 }
  ]
}
```

```powershell
$env:JIGU_GITHUB_API = "file:///D:/DSH/jigu-app_new/jigu-app/test-gh"
.\稽古.exe --test-update github:rdfghjgyuytytrudthgc/jigu-app
```

这条路径会一并验证「Release 里没有 app_version.json」时的推导回退
（版本取 tag、哈希取 `SHA256SUMS.txt`）。

### 独立探针

`tests\` 下有几个手工编译的检查程序，不需要 GUI 也不需要联网：

| 探针 | 校验什么 |
| --- | --- |
| `AssetCheck.exe <exe> <报告>` | 界面资源全部能从内存索引解析（防 `ERR_FILE_NOT_FOUND`） |
| `JsSyntax.exe <项目根>` | 前端资源齐全、括号配平、关键函数齐备 |
| `DataCheck.exe [根目录]` | 语料五要素齐全、标签齐备、UTF-8 中文完好 |
| `PendingCheck.exe [exe]` | **待应用更新的跨会话判定**：下好的包认得出、陈旧/损坏/半截包清得掉 |
| `UpdateLockCheck.exe [exe]` | **多开时的更新互斥**：同目录只让一个实例下载/替换，不同目录互不干扰 |

编译示例（in-box 编译器，无需装 SDK）：

```powershell
csc -out:tests\PendingCheck.exe tests\PendingCheck.cs
```

## 五、发版

### 版本号只有一个真源

`build.ps1` 顶部的 `$version` 是唯一需要改的地方。它会生成 `src\Version.g.cs`，
程序本体（`AppVer.Number`）与安装向导（`SetupInfo.Version`）都引用
`BuildInfo.Version`，**不再需要手工同步多个地方**。

CI 会做一道闸门：**tag 必须等于 `v$version`**，不一致直接失败。
这是有意的 —— 版本号忘改的后果不是报错，而是发出去的包永远提示有新版本、
装完又回到旧版本号，无限循环。

### 全自动流程

一条命令（VS Code 里就是任务 **稽古: 发布新版本**）：

```powershell
# 在源代码管理面板提交并同步之后：
powershell -NoProfile -File tools\release.ps1
# 忘了改版本号时：自动 +1 修订号、提交这一次改动、再发布
powershell -NoProfile -File tools\release.ps1 -Bump patch
```

它会校验分支 / 未提交改动 / 版本号 / 远端是否已有同名 tag，然后推 `main`、打 tag
`v<版本号>`、推 tag。等价的手工步骤是：

```powershell
# 1. 改 build.ps1 顶部的 $version，提交
# 2. 打 tag 并推送
git tag v1.7.0
git push origin v1.7.0
```

之后 `.github/workflows/release.yml` 全自动完成：

1. 构建 → `--selfcheck` 冒烟；
2. 生成新的 `app_version.json`（`notes` 优先取 `CHANGELOG.md` 里该版本的小节，
   没有就取上一个 tag 以来的提交标题，再没有才是一行 `稽古 v1.7.0 发布`）；
3. 算 `SHA256SUMS.txt`（覆盖 Release 上的每个文件）；
4. 建 Release 并挂上：安装包、便携包、`SHA256SUMS.txt`、
   **`app_version.json`、`data_version.json`、`corpus.json`、`labels.json`、`stopwords.json`**。

挂上后，默认的 `github:` 更新源对**程序本体与史料两条通道**都零配置可用。

也可以从 Actions 页手动 `workflow_dispatch` 指定一个已存在的 tag 重跑。

### 发版检查清单

- [ ] 改 `build.ps1` 顶部的 `$version` 并提交（或直接 `tools\release.ps1 -Bump patch`）
- [ ] 跑 `tools\release.ps1`（它自己做 `git tag vX.Y.Z && git push origin vX.Y.Z`）
- [ ] 等 CI 绿（tag 与版本号一致性闸门会先拦一道）
- [ ] 到 Release 页面确认 `app_version.json` 在附件里，且 `version` 与 tag 一致
- [ ] 在一台旧版本机器上启动，确认弹窗出现、点击后能自动更新并重启
- [ ] 若史料有变动：本次 Release 已自动带上新的 `corpus.json` 与 `data_version.json`，
      无需额外操作

## 六、安全边界（请如实告知使用者）

* **`sha256` 与安装包同源**：它能防下载截断、损坏与中间人替换（在 HTTPS 之外多一层），
  但**不能防发布账号本身被攻破** —— 清单和包都在同一个 Release 里，改一个就能改另一个。
  真正的防篡改需要内置公钥签名，**当前版本没有做**。
* **不会降级**：远端版本不高于本地时一律忽略，所以即使有人把旧版本标成 `latest`
  也只会被无视。
* **无认证 API 限流**：60 次/小时/IP。程序做了缓存（5 分钟）与周期复查（6 小时），
  并会在 403 时静默降级；同一出口 IP 后面用户量很大时建议改用静态基址源。
* **`update_base.txt` 不会被更新覆盖**：热替换时安装目录里已存在的
  `update_base.txt` / `data_base.txt` 会被跳过，自定义的更新源不会被静默改回默认值。
  代价是：**以后若想通过新版程序改变默认更新源，老安装不会自动跟随** ——
  这是有意的，编译内的默认值才是可随版本变化的那份。

## 七、多开与并发

程序可能被开成多份（用户双击两次、或从快捷方式与便携包各开一次）。同时更新
同一个安装目录会互相覆盖 `pending` 包、并各自拉起一个替换助手去改同一批文件。

为此「下载 + 替换」整段由命名互斥量 `Local\JiguUpdate-<安装目录哈希前16位>` 串起来：

* 抢不到的实例**静默退让**，不做任何提示 —— 抢到的那个下好后，`pending` 包是共享的；
* 装在不同路径的副本锁名不同，互不影响；
* 路径大小写、结尾反斜杠的差异会归一到同一把锁；
* 应用更新时持有锁直到进程退出，防止另一个实例在替换中途也去动文件。

同时*最小化到托盘常驻*的程序每 **6 小时**会重新检查一次，不必重启才能发现新版本。
