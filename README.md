# 稽古 · 二十四史情境检索（Windows 桌面版 0.1.0）

用中文写下你的困境，本机检索 201 则史事（先秦 → 清），给出**最相似的三条**。
**运行时不调用任何 AI 接口。**

> 说明：当全库确实找不到第三条相关史料时，只返回能找到的条数，**不拿无关条目凑数**。
> （实测「骨干员工要离职，留不住人」在补齐同义词前只能命中 2 条。）

> 各版本改了什么见 [CHANGELOG.md](CHANGELOG.md)（也是自动更新弹窗里那段说明的来源）；
> 发版流程见 [RELEASE.md](RELEASE.md)。

# 一、架构（v1.6 重构，0.1.0 修订）

## 1. 检索计算整体搬到 C#（前端不再参与计算）

| 层次 | 职责 |
| --- | --- |
| 前端 `web/app.js` | 只做三件事：收集输入、调用宿主、渲染返回的 JSON。**没有分词、没有加权、没有规则匹配** |
| C# `Corpus.cs` | 规范化 → 分词 → 查倒排索引 → IDF 加权 → 同义词桥扩展 → 取 Top3（全部本地算法） |
| C# `Synonyms.cs`（在 `Corpus.cs` 内） | 用户语言 ↔ 史料主题词的对照表，检索的第二条通路 |
| C# `JsonScan` | 逐条解析语料文件；每条文档的起止偏移一并返回，供热更新的按书合并原样抠出 JSON 文本 |

**前端有两份检索实现，必须说清楚**：`web/app.js` 里的 `localSearch` 是一份**独立而简化**
的 2 字滑窗检索，只在**拿不到宿主桥**时启用（系统浏览器兜底、或桥注册失败）。
它与 C# 引擎的排序**不一致**、精度更低，界面上会标注「离线模式 · 精度低于内置界面」。
不把它与 C# 引擎对齐是刻意的：跨语言对齐等于永远维护两份必须同步的算法。

### 三条结果按什么排序

对每个查询词元 `t`（分词得到的 + 同义词桥扩展的）：

```
idf(t) = ln((N+1) / (df(t)+1)) + 1      N = 文档总数，df = 含 t 的文档数
权重   = idf(t) × 1.35（t 长 ≥3 字）× 0.75（t 来自同义词扩展）
凡含 t 的文档 → 得分 += 权重
```

然后：**得分降序 → 同分时命中词数多者优先 → 再同分才按文档号**。
不足三条时用 2 字滑窗补足（0.5 权重，排在后面）。

**它本质是「命中词的稀有度之和」，不是语义相似度。** 界面上的「关键决策」等字段只是
获胜那条史料的内容，**不参与打分** —— 没有字段加权（见下表：乘性字段权重实测是负收益）。
所以排序质量的上限由两件事决定：①查询词元切得对不对（分词器 + 停用词表）；
②语料里的主题词标注够不够密（`themes` + 标签表）。**调 idf 公式本身收效甚微。**

## 决策分析栏

每条结果的最后一块是**决策分析**：左栏「这么做的好处」、右栏「这么做要付的代价」，
再加一行「与你的处境对应」—— 把这条史料带的情境标签中、**原样出现在用户输入里**的那几个
标出来（纯子串比对，运行时算）。

利/弊正文是**随语料离线写好的**（每条史料的 `pros` / `cons` 两个字段），运行时不生成
任何文字 —— 这是「不调用 AI」前提下的必然做法。写法上，pros 写「这个决策在什么条件下
成立、当事人得到了什么」，cons 写「付出了什么代价、依赖什么前提、什么情况下会反过来
失败」，只依据该条自带的原文/译文/决策/结果，不引入史料外的事实。**程序不下结论**：
哪一边更重取决于用户自己的处境。

## 2. 数据外置 + 倒排索引

* 史料合并为 exe 同目录的**单个 `corpus.json`**（201 条 / 251 KB），**不内嵌**在 exe 里；
  合并时按**原文逐字比对去重**（种子卷与分卷曾各存一份，原始 204 条里实际是 201 条不同史料，
  重复条目会占掉 Top3 的两个位置）；
* `corpus.json` 缺失时才回落到内置的 `seed.json`（仅 19 条），保证开箱可用；
* `labels.json`（情境标签表）与 `stopwords.json`（查询停用词表）同样外置优先、内嵌兜底，
  且列入热更新的平文件清单 —— 扩表不必重新编译；
* 索引只存 `词 → [文档号]`；
* **正文是常驻内存的**：每条 `CorpusDoc` 完整持有原文/译文，全部 201 条留在 `_docs` 里。
  251 KB 的量级下这完全没问题，所以不再假装「正文只在解析期间存在」；
* 词表 45,416 词、倒排表约 2.9 MB。

**实测**：201 条语料 → 索引 45,416 词 / 2.9 MB；6 条长查询检索耗时 **0~9 ms**。

## 3. 双路热更新

| 通道 | 清单 | 行为 |
| --- | --- | --- |
| 史料数据 | `data_version.json` | 启动**静默**比对 Hash → 只下载变化文件 → 校验 SHA-256 与 JSON → 按 `book` 合并进 `corpus.json` → 重建索引 → 界面自动刷新。失败静默降级 |
| 程序本体 | `app_version.json` | 启动检查 → 版本更高则**当场弹窗**告知新增内容 → 用户点「是」→ 后台下载（界面显示进度）→ 校验 SHA-256 → 下好**再问一次**是否立即重启 → 启动替换助手 → 等主进程退出 → 覆盖文件 → **自动重启** |

替换助手就是把当前 exe 复制到临时目录、以 `--apply-update <安装目录> <新包> <pid>` 运行；
新安装包自身支持 `--extract-to <目录>` 自解压，所以热替换不依赖任何第三方安装器。

## 4. 系统自适应

* 启动时用 `Environment.OSVersion` 判断 Windows 版本与架构，低于 Win7 给出友好提示而非崩溃；
* 路径**全部**基于 `AppDomain.CurrentDomain.BaseDirectory`（相对基准），
  代码中不存在 `C:\Program Files` 这类绝对路径；
  （0.1.0 修正：**构建脚本** `build.ps1` / `tools\make-icon.ps1` 曾硬编码 `D:\DSH\jigu-app`，
  换台机器就编译不了。已改为从 `$PSScriptRoot` 推导，现在这句才是真的。）
* 工作目录按可用性回退：用户数据目录 → 程序同目录 → 临时目录；
* WebView2 三重检测（注册表 64/32 → 安装目录 → 目录名），缺失时引导一键安装；
* **WebView2 用户数据目录固定为 `%LOCALAPPDATA%\Jigu\WebView2`**（纯 ASCII、无空格）。
  含中文/空格的路径会被 WebView2 的参数校验拒掉并抛 `ArgumentException（值不在预期的范围内）`，
  所以程序只从 ASCII 候选里挑，且逐个试写探针，任何一个不可用都继续下一个；
* 渲染进程老生代限制 128 MB，避免 WebView2 侧无限膨胀。

**已知缺陷：OS 版本会误报。** exe 没有 manifest（构建时未传 `/win32manifest`），
于是 `Environment.OSVersion` 在 Windows 10/11 上返回 `6.2.9200`，报告里显示成
`Windows 6.2.9200(8)`。只影响显示文本（`Sys.IsSupported()` 走 `Major==6 && Minor>=1`
分支仍然返回 true，没有功能性后果），但会把排查引向错误方向。修法：加一份声明
supportedOS GUID 的 manifest（顺带解决高 DPI 下界面发虚）。

## 5. 启动链路回滚 + 三级兜底（v1.6.1，针对"窗口创建失败/值不在预期的范围内"）

启动顺序被压到最小：**窗口先出来，其它全部后置**。

| 阶段 | 做什么 | 绝不做什么 |
| --- | --- | --- |
| `MainForm` 构造 | 只建窗口、放一个"正在备书"标签 | 不读语料、不建索引、不联网、不建托盘 |
| `OnShown` | 起后台线程（语料/索引/更新/托盘）+ 初始化 WebView2 | 不阻塞界面线程、不递归重试 |
| `OnCoreReady` | 只做：设置项 → 注册内存资源应答 → `Navigate(index.html)` | 不再做数据/更新工作 |

`CoreWebView2Environment.CreateAsync(null, dir, new CoreWebView2EnvironmentOptions())` 只传**默认参数**：
不传浏览器可执行文件路径，也不再传含转义引号的 `--js-flags` 一类字符串
（历史版本正是这类参数在部分运行时上被参数校验拒绝）。

初始化失败按三级兜底，任何一级都不会把用户丢在空窗口里：

1. **失败页**（古风页面，含具体异常类型/消息、WebView2 检测结果、`error.log` 路径），
   提供「改用内置界面」「复制错误」两个按钮；
2. **内置原生界面** `ClassicForm`：纯 WinForms 绘制，不依赖 WebView2，
   同样的输入框 / Top3 卡片（原文摘录·现代文翻译·核心人物·关键决策·最终结果·决策分析）；
3. **系统浏览器** `ClassicUI`：把内置界面落盘到可写目录（`%LOCALAPPDATA%\Jigu\web`
   → 临时目录 → 程序目录），再用系统默认浏览器打开；页面在无宿主桥时
   从同目录 `corpus.json` 现场建 bigram 索引，离线也能查。

诊断能力（无需用户做任何设置）：

* `error.log`（程序目录，只读安装时自动改写到 `%LOCALAPPDATA%\Jigu`）：
  无条件记录异常类型、消息、**完整 StackTrace**、内部异常、系统信息；
* `jigu-debug.log`（写在 `%LOCALAPPDATA%\Jigu\`）：
  记录启动全过程，包括
  `userDataDir chosen` → `CreateAsync userDataFolder=` → `environment ready, browser=` → `fatal page shown`；
  （0.1.0 修正：`Log.Init` 原先排在 `PickUserDataDir` 之后，而后者内部就会写一行诊断，
  于是那一行被回退逻辑单独写到了 exe 旁边，形成两个同名日志文件、而窗口标题指向的那份里反而没有它。
  现在 `Log.Init` 在最前，只有一份日志。）
* 窗口标题会带上当前日志文件路径，出问题时看一眼标题就知道日志在哪。

### ⚠ 上面这一段的诊断方向是错的（0.1.0 更正）

在**真实桌面**上（WebView2 正常安装、正常初始化）程序**必然**弹失败页，报
`ArgumentException: 值不在预期的范围内`。历史版本把它当成「WebView2 初始化失败 / 参数校验拒绝」
来修，所以整节都在调整 `CreateAsync` 的参数 —— **方向错了**。

真因在 `OnCoreReady` 里，而且它恰好是**初始化成功之后**才会执行到的那一段：

```
error.log 实测堆栈：
  at CoreWebView2.AddHostObjectToScript(...)
  at Jigu.MainForm.OnCoreReady(...)
```

`HostBridge` 声明在 `internal sealed class MainForm` **里面**。嵌套在 internal 类里的 public 类，
对外实际可见性仍然是 internal；而 **COM 看不见 internal 类型**，无法为它生成 IDispatch，
于是 `AddHostObjectToScript` 抛 `E_INVALIDARG`。
**与 WebView2 无关，改一个词就好**：`MainForm` 由 `internal` 改成 `public`。

为什么一直没被发现：`OnCoreReady` 的这段代码只在 **WebView2 初始化成功**时才执行，
而当时的测试环境（沙箱禁止创建 Chromium 所需的命名管道）里 WebView2 **必然**初始化失败 ——
于是失败路径被反复验证，成功路径从未被执行过一次。

0.1.0 一并做了两件事，让这类问题不再致命：

1. **桥注册失败不再拖垮整个网页界面**：`AddHostObjectToScript` 单独 try/catch，失败只记日志、
   继续 `Navigate`，页面自动降级到「读同目录 `corpus.json` 现场建索引」的离线模式。
   `JIGU_NO_BRIDGE=1` 环境变量可强制跳过注册，随时复验这条降级路径。
   （降级之所以能生效，还因为修好了 `app.js` 的桥探测：**宿主对象没注册时，
   WebView2 的 `hostObjects.host` 依然返回一个真值代理而不是 undefined**，
   所以「`host()` 非空」不能证明桥可用 —— 只能靠真实调用的结果判断。）
2. **`OnWebResourceRequested` 增加磁盘平文件白名单**（`corpus.json` / `data_version.json`，
   取自 `BaseDirectory`，与语料和更新的基准目录一致），否则离线兜底拿到的只会是 404。

# 二、检索质量修复（0.1.0）

v1.6 把算法从前端搬到 C# 时，只搬了一半：搬走了 IDF，丢掉了四个让检索真正能用的机制。
后果是**首页自带的 4 个示例问题里有 3 个结果是错的**。0.1.0 修的就是这些。

## 修了什么

| 缺陷 | 真因 | 修复 |
| --- | --- | --- |
| 「互相猜忌」检索不到 `陈平反间`/`沙丘之变` | `Tokenize` 的兜底分支**不查词表**就吐 2 字窗口并前进 2 字，于是吐出词表里并不存在的 `相猜`、跳过相邻的「忌」，`猜忌` 永远进不了词元表 —— 正确答案就在库里，却从未被检索 | 命中不了时只前进 1 字、不吐词元；整句切不出来时才回落 2 字滑窗 |
| 用户说「合伙人反目」这类自己的话检索不到东西 | **同义词表从未被任何代码读取**。而且它的组键本身就是用户语言（合伙人反目/被人挑拨/骨干离职），分词器永远不会把它们切成词元，所以「查词表」这种接法基本不触发 | 新增同义词桥：对**归一化整句做子串扫描**触发，扩展词按 0.75 折算 |
| `现金流` 这类词几乎检索不动 | `EmitBlock` 对长度 > 4 的块**一个 3 字词元都不产生**，一半的 4 字词元也不产生 —— `现金流` 全库 df 只有 1 | 改成 2~4 字全滑窗（词表 24,356 → 44,256，`现金流` df 1 → 5） |
| 同分时「每次都是那几条」 | 排序并列时按文档号决定 | 先比命中词数，再比文档号 |
| **关键词被现代虚词挤掉** | 排序是「命中词的 IDF 之和」，而 IDF 奖励的是**在语料里稀有**。`互相 / 不断 / 已经 / 有人` 这类现代虚词在文言语料里 df 只有 2~4 → idf 4.4~4.9，比 `猜忌`（df=5, idf=4.50）还高，于是靠数量优势把关键词压下去。实测库里有 5 条含「猜忌」的史料（陈平反间 / 沙丘之变 / 自毁长城…）**一条都没进前三**，赢的是 八王之乱 / 三不如 / 鸿门宴 | 新增**查询侧停用词表** `stopwords.json`（72 词），分词后命中即丢弃。实测 Top3 变为 萧何月下追韩信（骨干离职）/ 陈平反间 / 己巳之变与反间（后两条都是「猜忌」）。**这不是调参能修的**：公式给「不断」高分是它的正确行为，错把无信息的词当成有信息的词 |
| 只有一个词元能命中时结果全是无关条目 | 裸 idf 求和，没有补足机制 | 主词元命中不足三条时用 2 字滑窗补足差额（0.5 权重，不打扰已排好的结果） |
| 字段加权一直是空操作 | 调用处传了 4/1/2/3 的权重，但 `AddTerms` 的 `weight` 参数**在函数体里从未使用**，且 sink 是 HashSet（去重） | **删掉死参数**，不实现它 —— 实测乘性字段权重是负收益（把通用词的命中数量优势进一步放大，反而盖掉 IDF 的区分度）。想表达「策展字段更重要」，正确做法是走同义词桥 |

**明确不做**：`MIN_VOCAB_FREQ=2` 词表过滤（实测 8 组配置全部 -1；201 条语料下 df=1 恰恰最有区分度，
而且垃圾词元是查询时生成的，过滤索引根本管不到）；文档长度归一化（正文平均仅 122 字，因子近似常数）。

## 回归护栏

`稽古.exe --selfcheck 报告.txt` 的第 3 节现在是**召回回归**，用例来自 `tests/cases.json`
（构建时内嵌进 exe，所以在发行版上也能跑 —— 静默跳过的护栏等于没有护栏）。

* 判定：`want` 里任意一项作为子串出现在 Top3 标题中即通过（宽松判据，避免每次调权重都要改期望值）
* 硬失败：返回超过 3 条；**已核对的用例**未命中
* 只报告：返回少于 3 条（全库可能确实只有那么多，凑数更糟）
* 边界用例：空串 / 纯空白 / 全角空格 / 纯英文数字 / 单个汉字 / 300 字重复，不得抛异常、不得超 3 条
* **`--selfcheck` 现在会设置退出码**（失败非 0，成功 0），可直接用于 CI

### 用例的两种置信度，报告里分开计

| 标记 | 含义 | 作用 |
| --- | --- | --- |
| `PASS` | `confidence: high` —— 期望值人工核对过，确认是该问题的正解 | 召回质量护栏 |
| `PASS~` | `confidence: snapshot` —— 期望值取自 0.1.0 引擎的实际输出并人工抽查认可 | **变更探测器**：保证后续改动不会悄悄改变结果，但**不宣称**这组答案优于其他答案 |
| `REVIEW` | `confidence: low` —— 期望值没核对过，只报告、不计入失败 | 待人工判断 |

`PASS~` 这一档是刻意分开的。把「引擎当前的输出」当成「正确答案」写死进 `want`，如果不加标注，
就是在拿测试迁就代码；标成快照之后它仍有价值（改动会被发现），但不会被误读成品质量断言。
总结行会写明有几条是快照。

**别忘了**：错的期望值比没有期望值更糟 —— 它会训练人忽略红色。所以宁可少写几条、每条都亲自读过那三条史料，
也不要凑数量。复核与新增方法见 `tests/cases.json` 的 `review_guide`。

### 当前两处已知的数据缺口（不是代码问题）

| 用例 | 现象 | 性质 |
| --- | --- | --- |
| Q2 | `现金流` 只在同义词组的触发侧起作用，靠 `粮尽`/`军需不继` 间接命中 | 同义词表成员在语料里缺落点 |
| Q4 | `投诉` / `挑拨` 在语料里 **0 条落点** | 同上；靠 `约法三章`/`水能载舟` 兜住 |

## 情境标签表是产品的核心资产

`labels.json`（**75 个标签**）是连接「用户的现代说法」和「史料标注」的**唯一通路**。
检索算法只是把标注里已有的相似性检索出来，它**不能创造相似性** —— 所以这张表的持续扩充
比继续优化 IDF 公式值钱得多。

### 结构：一个标签 = 一个情境，带一批「触发说法」

```json
{ "label": "骨干离职",
  "triggers": ["员工要离职", "留不住人", "骨干要走", "谋臣出走", "挂印而去", ...] }
```

用户说任何一种 trigger → 命中标签 → 把**标签名**并入查询。史料挂的就是标签名。

### 三条硬规则（都是踩出来的）

1. **标签名必须 ≤4 字。** 索引最长只发 4 字词元，超了连标签名自己都进不了索引，等于白建。
   为此 `合伙人反目`→`反目`、`改革推不动`→`改革受阻`（原名保留为 trigger）。
2. **史料要挂两层**：粗标签（负责「对得上」）+ 原有细 themes（负责「分得开」）。
   只挂粗标签实测会把区分度搞丢 —— `将帅不和`(df=3, idf 5.19) 被并成 `内部矛盾`(df=46, idf 2.46) 后，
   `将相和` 直接从「团队矛盾」的 Top3 里消失了。
3. **trigger 不在语料里是正常的**，别把它当死条目 —— 它就是「用户会怎么说」（如 `留不住人`）。
   方案 B 下并入查询的是标签名，trigger 只负责找路。

### 怎么扩充（不用重新编译）

`labels.json` **外置优先**：把新版丢到 exe 同目录、重启即生效；没有外置文件时才用内嵌的那份。

也可以走热更新：`data_version.json` 的 `files` 段（平文件 `name → sha256`，直接下载覆盖，
不参与按书合并），相对路径复用 `paths` 映射。端到端验证过：
`filesChanged=1 → filesUpdated=1 → 重载后生效`，第二次运行 `filesChanged=0` 不重复下载。

**注意**：`Apply` 的触发门槛必须同时看「史料变化」和「平文件变化」。只看前者的话，
「只更新了标签表」这类更新会被静默跳过、永远不生效 —— 实现时踩过并已修掉。

### 体检与扩充的方向

`--selfcheck` 里有一行摘要（标签数 / trigger 数 / 其中多少在语料里存在），**表为空直接判失败**。

要动手扩充时，两张表比什么都直接：

* **没有史料挂靠的标签** → 说明语料缺这类案例（当前 6 个：培养人 / 功成身退 / 退出机制 / 反目 / 风险管理 / 外交）
* **trigger 在语料里没有对应词** → 说明史料标注缺这类词汇

`tests/DataCheck.cs`（手工 `csc /out:DataCheck.exe DataCheck.cs`，用法 `DataCheck.exe [项目根目录]`）
会把这两类逐条列出来。

# 三、crash 修复要点（v1.6.1）

| 现象 | 真因 | 修复 |
| --- | --- | --- |
| 运行一会 OOM（真因 1） | `ShowFatal` 每次都 `new Panel` 挂窗体（旧面板不释放），失败页的「重试」再次失败又递归触发 `ShowFatal` → 无限重试 + 控件堆积 | 失败页只允许出现一次；重试计数封顶；已存在面板则直接复用 |
| 运行一会 OOM（真因 2，更隐蔽） | **WebView2 在初始化失败时会重复触发 `CoreWebView2InitializationCompleted`**。日志实测同一进程内被触发两次（间隔 1.5s），每次都会重新构建内核对象与面板，最终内存被拖爆 | `OnCoreReady` 增加 `_coreHandled` 重入守卫，只处理第一次；`StartInit` 同时校验「已尝试 / 已显示失败页 / 已处理核心回调」三个条件后直接跳过 |
| 进程莫名退出 | 上述重复回调后窗体被关闭 | 守卫生效后进程稳定存活（实测 10 分钟） |
| 顶部弹原始 JSON（`remoteObjectId` / `0x80070490`） | 数据更新后用 `ExecuteScriptAsync` 注入脚本，页面未就绪时 WebView2 返回原始对象并被当成消息显示 | 删除脚本注入，改为前端每 60 秒轮询宿主标志；新增 `FriendlyText()` / `friendly()` 把这类内容一律转成中文提示 |
| 前端脚本报错 | DOM 操作未等就绪；`String(errorObject)` 产出 `[object Object]` | 全局 `ready(boot)` + `$(id)` 空值兜底 + `bind()`；`errText()` 覆盖 Error/字符串/含 message·reason·error·code 的对象 |
| 前端内存增长 | 藏书阁一次性渲染全部行；定时器无登记 | 藏书阁**每页 20 项**分页；所有 `setTimeout` 走 `later()` 登记，`beforeunload` 全部 `clearAllTimers()` |

## 卸载会清空安装目录（0.1.0 加护栏）

安装目录由用户任选，而卸载程序原来无条件执行 `rmdir /s /q <安装目录>`。
**如果用户把程序装在「桌面 / 文档 / 盘根」这类本来就有自己文件的地方，卸载就会连同那里一起清空**
（实测：装到桌面再卸载 → 整个桌面被删）。

现在卸载前先确认目录里**每一项都是我们装的**（子目录只认 `data/`，判不准就一律按不是处理）：

* 是 → 照旧递归删除整个目录；
* 否 → **只删我们的文件，绝不删目录本身**，并提示「该目录还含其它文件，为安全起见没有删除目录」。

顺带修掉一个遗留问题：删目录的 `cmd` 自己的工作目录就在安装目录里（继承自快捷方式的工作目录），
而 Windows 不允许删除任何进程的当前目录 —— 不先 `cd` 走，`rmdir` 会删光内容却留下一个**空目录**。
现在 cmd 先切到临时目录，常规安装卸载后目录真正消失。

护栏的两条分支都在临时沙箱里实测过（含一个"诱饵"用户文件）：含诱饵时目录与诱饵均保留、我们的文件被清除；
只有我们的文件时整个目录被删除。

# 六、开发者：怎么托管更新文件

见 `docs\更新服务托管说明.md`，要点：

1. **默认什么都不用配**：更新源是 `github:1279255198psy/jigu-app`，读的是最新
   Release 的附件。打一个 tag（用 `tools\release.ps1`，见第七节），CI 就会把
   `app_version.json`、`data_version.json`、
   `corpus.json`、`labels.json`、`stopwords.json` 一起挂上去，程序本体与史料两条通道
   立刻可用。**不需要服务器程序、不需要数据库**。
2. **想自建镜像**：把这些文件传到任意静态空间（阿里云 OSS / Nginx 目录 / 内网共享均可），
   把地址写进 exe 同目录的 `update_base.txt`（`https://…` 或 `file://…`），
   `dist\update\` 整个目录就是现成的上传内容。
3. **想给史料单独走一个源**（数据迭代频率远高于程序本体）：再放一个 `data_base.txt`。
4. 更新地址优先级：`JIGU_UPDATE_BASE` → `update_base.txt` → 编译内默认值，
   代码内无绝对路径。
5. **热替换不会覆盖这两个文件**：安装目录里已有的 `update_base.txt` / `data_base.txt`
   会被跳过，自定义源不会被静默改回默认值。

**用户侧发生什么**：启动后台检查 → 程序本体有新版本就**当场弹框**问要不要现在下载
（只花一次检查的时间，不等下载）→ 下好再问一次「新版本已下载完成，现在重启更新吗？」。
第一问点「否」就不下载，下次启动再问。最小化到托盘常驻时每 6 小时复查一次，
那次不弹框、只静默预下载。史料通道全程静默；网络失败不当场报错，
但用户点过「要更新」的下载失败会说明并给一次重试。

**情境标签表与停用词表不随包出厂**（外置优先、内嵌兜底），所以刚装好的程序会去源上
取一次这两张表；之后想单独更新它们，既可以直接放到 exe 同目录重启生效，
也可以在 `data_version.json` 的 `files` 区段里下发（`files` 是整体替换的平文件，
与 `books` 的「按书合并」不同）。

# 七、发版与自测命令

**发布一条命令**：在 VS Code 的源代码管理面板提交并同步，然后跑任务
**稽古: 发布新版本**（`Ctrl+Shift+P` → `Tasks: Run Task`），或者直接在终端：

```powershell
powershell -NoProfile -File tools\release.ps1            # 会先问版本号，再发布
powershell -NoProfile -File tools\release.ps1 -Version 0.1.1  # 不问，直接指定
powershell -NoProfile -File tools\release.ps1 -Bump patch  # 不问，自动 +1 修订号
powershell -NoProfile -File tools\release.ps1 -DryRun      # 只检查，什么都不改
```

**不用手工改版本号**：定了号之后，脚本自己把 `build.ps1` 和 `CHANGELOG.md` 的标题改好
并一起提交（CI 构建的是 commit，留在工作区里的改动不会进包）。

脚本自己判断该不该发（分支、未提交改动、版本号、远端是否已有这个 tag），
推 tag 之后由 CI 构建并发布。完整说明见 `RELEASE.md`，脚本的取舍见它开头的注释。

| 命令 | 作用 |
| --- | --- |
| `tools\release.ps1` | **发布**：问版本号 → 改 `build.ps1` 与 `CHANGELOG` 标题并提交 → 推 `main` → 打并推 tag `v<版本号>` → CI 自动构建发布 |
| `稽古.exe --selfcheck 报告.txt` | 界面资源 / 语料与同义词表 / **召回回归**（读内嵌的 `tests/cases.json`）/ 更新清单。**失败时退出码非 0** |
| `稽古.exe --test-update <地址>` | 走完检查→下载→校验→解压替换全流程（不弹窗） |
| `稽古.exe --built-in [url]` | 直接开内置 WinForms 界面（不碰 WebView2），用于诊断 |
| `稽古.exe --web-fallback` | 把网页界面落盘并用系统浏览器打开（WebView2 完全不可用时的最后兜底） |
| `JIGU_NO_BRIDGE=1 稽古.exe` | 强制跳过宿主桥注册，复验「离线模式降级」这条路径 |
| `稽古-安装包.exe /silent /dir=<目录>` | 静默安装 |
| `稽古-安装包.exe --extract-to <目录>` | 自解压（热替换使用） |
| `稽古-卸载.exe /uninstall /silent` | 静默卸载 |

`tests\` 下的独立探针（手工 `csc` 编译，不需要 GUI、不需要联网）：

| 探针 | 作用 |
| --- | --- |
| `AssetCheck.exe <exe> <报告>` | 界面资源全部能从内存索引解析（防 `ERR_FILE_NOT_FOUND`） |
| `JsSyntax.exe <项目根>` | 前端资源齐全、括号配平、关键函数齐备 |
| `DataCheck.exe [根目录]` | 语料五要素齐全、标签齐备、UTF-8 中文完好 |
| `PendingCheck.exe [exe]` | 待应用更新的跨会话判定：下好的包认得出，陈旧/损坏/半截包清得掉 |
| `UpdateLockCheck.exe [exe]` | 多开时的更新互斥：同目录只让一个实例下载/替换，不同目录互不干扰 |
| `IconCheck.exe <项目根>` | 图标是古风印章而非默认图标，且 exe／安装包／负载／交付目录四处一致 |
| `InstallerLogicCheck.exe [沙箱目录] [应用目录]` | 快捷方式与卸载注册项读写、交付目录文件齐全（应用目录省略时沿用沙箱） |
| `OffsetCheck.exe [corpus.json]` | 扫描器给的下标是**字符**下标，切片必须切同一个字符串 —— 单位搞错会把语料切坏 |
| `ParseCheck.exe` | 解析层健壮性：带 BOM 的语料／标签照样解析；深嵌套降级成「解析失败」而不是爆栈杀进程 |
| `UninstallCheck.exe` | 卸载判定：只有整目录都是我们的才敢整目录删；用户往里放过任何东西都退化成「只删我们的文件」 |

`ParseCheck` 与 `OffsetCheck` 一样只依赖 `src\Json.cs` + `src\MiniJson.cs`：

```
csc -nologo -out:ParseCheck.exe ParseCheck.cs ..\src\Json.cs ..\src\MiniJson.cs
```

`UninstallCheck` 特殊一点：它要和**安装向导那一遍的源码**编在一起（要读真的载荷键表，
并经反射调用 `UninstallForm` 的私有判定方法；`UninstallForm` 在 `JiguSetup` 命名空间，
`InstallerPayload` 在 `Jigu`）。载荷键表来自 `/resource:` 的那个 zip —— 所以这条命令
要先跑过 `build.ps1`（`obj\payload.setup.zip` 是它生成的），漏掉 `/resource:` 时探针会
直接报「载荷键表为空」而不是在空夹具上假绿：

```
csc -nologo -out:UninstallCheck.exe /main:Jigu.UninstallCheck UninstallCheck.cs ^
    ..\src\Installer.cs ..\src\SetupAssemblyInfo.cs ..\src\Host.cs ..\src\Update.cs ^
    ..\src\Json.cs ..\src\MiniJson.cs ..\src\Corpus.cs ..\src\Library.cs ..\src\PayloadExt.cs ^
    ..\src\EmbeddedAssets.g.cs ..\src\Version.g.cs ^
    /resource:..\obj\payload.setup.zip,Jigu.payload.zip ^
    /reference:System.Windows.Forms.dll /reference:Microsoft.Web.WebView2.Core.dll ^
    /reference:Microsoft.Web.WebView2.WinForms.dll
```


另外两条与热更新合并有关的回归手段：

| 手段 | 作用 |
| --- | --- |
| `tests\make-merge-fixture.ps1` | 造一份**内容真的不同**的假远端（整份语料 + 一条按书下发的补遗，且文件名与书名故意不同） |
| `tests\compile-check.sh` | 两遍 `csc`（主程序 / 安装向导）的快速编译校验，不必跑完整 `build.ps1` |

> 夹具必须让语料**真的变化**再跑 `稽古.exe --test-update file:///<夹具>`：
> 内容一模一样的话更新根本不会执行，合并里的问题就永远看不出来。
> 判定标准是更新后条数不减少、**也不出现重复**（按错键时整份语料会被再追加一遍）。

> `tests\*.exe` 与 `tests\` 下的 WebView2 DLL 都不进版本库（见 `.gitignore`）。
> 源码改动后要**重新编译**再跑，否则跑的是旧断言 —— 这一点曾被旧二进制坑过。
